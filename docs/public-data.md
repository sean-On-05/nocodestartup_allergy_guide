# 공공 레시피 데이터 확보 및 반영

## 지금 사용할 수 있는 자료

식품의약품안전처 **조리식품의 레시피 DB (COOKRCP01)** 공식 샘플에서 음식 5개와 재료 36행을 확보했습니다. 생성한 예시 레시피가 아니라 공식 응답의 음식명·재료·분량을 보존한 자료입니다.

- [공공데이터포털 데이터 및 이용 조건](https://www.data.go.kr/data/15060073/openapi.do): 무료, 이용허락범위 제한 없음
- [공식 API 명세](https://www.foodsafetykorea.go.kr/api/newDatasetDetail.do?svc_no=COOKRCP01)
- [사용한 공식 샘플 응답](https://openapi.foodsafetykorea.go.kr/api/sample/COOKRCP01/json/1/5)
- 확인일: 2026-11-21

| ID | 음식 | 재료 행 |
|---|---|---:|
| mfds:28 | 새우 두부 계란찜 | 7 |
| mfds:29 | 부추 콩가루 찜 | 9 |
| mfds:31 | 방울토마토 소박이 | 10 |
| mfds:32 | 순두부 사과 소스 오이무침 | 4 |
| mfds:33 | 사과 새우 북엇국 | 6 |

**5개 공식 샘플만 확보했습니다. 전체 DB를 확보하거나 대표 한국 음식 전체를 지원한다고 주장하지 않습니다.** 영문 표시명은 앱에서 번역한 것으로 공식 번역이 아닙니다. 출처의 조리 지시문·사진은 재배포하지 않습니다. 영양값도 분량 기준이 충분히 확인되지 않아 UI에 추가하지 않았습니다.

## 웹앱에서 바로 이용

식재료는 실제 Supabase에서 읽습니다. 음식 테이블이 비어 있으면 위 공식 샘플을 앱에 포함된 자료로 표시하며, DB에 저장된 음식처럼 표시하지 않습니다. 음식명 검색 → 원본 재료 목록 → 연결된 식재료의 알레르기 안내 → 한국어 직원 확인 카드로 이어집니다.

이름을 완전히 일치시키거나 공백 차이만 있는 유일한 항목만 연결합니다. 모호하거나 찾지 못한 재료는 숨기지 않고 미연결로 표시합니다. 연결되더라도 전부 `needs_review`로 취급합니다. 원본의 원재료 명칭과 분량은 확인 화면에 남습니다.

직접 입력한 음식명이 정확히 등록된 참고 레시피와 일치하면 참고 자료를 보여줍니다. 이는 사진 AI 인식이나 해당 매장의 실제 레시피 확인을 의미하지 않습니다.

## Supabase에 저장하는 마지막 단계

공개 키로는 관리자 SQL을 실행할 수 없습니다. 비밀 키나 DB 비밀번호를 채팅으로 공유할 필요가 없습니다.

1. [실행용 SQL](../data/public-recipes/import-to-supabase.sql)을 열고 전체 내용을 복사합니다. GitHub에서는 Raw 버튼을 누르면 복사하기 쉽습니다.
2. Supabase 프로젝트 → **SQL Editor → New query**에 붙여넣고 **Run**을 누릅니다.
3. 완료 결과에서 `recipes = 5`, `ingredients = 36`을 확인합니다.
4. 웹앱을 새로고침하면 Supabase 음식 테이블을 우선 읽습니다. 상단의 음식 데이터 안내가 Supabase로 바뀝니다.

실행용 SQL은 프로젝트 소유자가 실행하는 자료입니다. 서버에 실행을 시도하지 않았습니다. 알려진 테이블 구조를 사용하되, 알 수 없는 필수 컬럼이 있으면 전체 트랜잭션을 중단합니다. 그 경우 오류 메시지를 공유하면 실제 스키마에 맞게 조정할 수 있습니다.

### SQL이 수행하는 작업

- 기존 `external_recipes`, `external_recipe_ingredients`에 출처 접두어 `mfds:`가 있는 새 레코드를 추가합니다.
- `external_ingredient_master_mapping`에 이름 비교 후보를 추가합니다. 미연결은 `ingredient_id = null`, 모든 새 후보는 `needs_review`입니다.
- `kfood_public_recipe_sources` 테이블을 추가해 원본 재료 문구·출처·이용 조건을 보존합니다.
- 추가한 공공 레시피와 관련 매핑만 대상으로 한 익명/로그인 사용자 SELECT 정책을 추가합니다. 공개 INSERT/UPDATE/DELETE 정책은 추가하지 않습니다. 기존 RLS를 끄지 않습니다.
- 기존 식재료 마스터·알레르기 근거를 변경하지 않으며 기존 매핑도 덮어쓰지 않습니다.
- 같은 SQL을 다시 실행하면 중복을 추가하지 않습니다. 기존 레시피 ID나 재료 행의 내용과 충돌하면 중단합니다.

실제 프로젝트의 숨겨진 제약조건까지 조회한 것은 아니므로 운영 DB에 실행 완료했다고 표시하지 않습니다. PostgreSQL 호환 테스트 환경에서 반복 실행, 충돌 시 중단, 미확인 필수 컬럼 중단, 익명 읽기 허용/쓰기 거부를 검증했습니다.

## 자료 파일과 재생성

- `data/public-recipes/mfds-sample.json`: 출처·이용 조건·원본 재료 문자열·구조화한 36행
- `external_recipes.csv`, `external_recipe_ingredients.csv`: Table Editor 수동 가져오기에 사용할 UTF-8 CSV. 출처 메타정보와 정책은 SQL에 포함돼 있으므로 SQL 실행을 권장합니다.
- `npm run prepare:recipes`: JSON에서 SQL을 다시 생성합니다. DB에 접속하거나 데이터를 쓰지 않습니다.
- `npm run check:connection`: 앱의 실제 어댑터로 Supabase를 읽어 음식 개수와 데이터 출처를 확인합니다.

## 더 많은 음식으로 확장할 때

기존 DB 스키마와 잘 맞는 자료는 농림수산식품교육문화정보원의 [레시피 기본정보](https://www.data.go.kr/data/15057205/openapi.do)와 [레시피 재료정보](https://www.data.go.kr/data/15058981/openapi.do)입니다. [제공기관 명세](https://data.mafra.go.kr/opendata/data/indexOpenDataDetail.do?data_id=20150827000000000465)에서 `RECIPE_ID`로 연결되고, 재료명·순번·분량이 분리돼 있음을 확인했습니다. 공개 `sample` 키는 1~5 범위만 허용되므로 그 제한을 넘어 전체를 내려받지는 않았습니다. 전체 수집에는 본인 계정으로 발급한 정식 API 키나 공식 다운로드 파일이 필요합니다.

식약처 데이터도 정식 API 키 발급 후 수집 범위를 확장할 수 있습니다. 그때 공급자 접두어가 다른 ID를 보존하고, 원본 재료를 모두 가져온 다음 미연결 재료를 검토해야 합니다. API 키는 서버/수집 환경 변수로 보관하며 `VITE_` 변수로 공개하지 않습니다.

### 검토했으나 채택하지 않은 자료

- 농촌진흥청 [한식요리정보](https://www.data.go.kr/data/15137355/fileData.do)·[한식 재료 정보](https://www.data.go.kr/data/15137344/fileData.do): 파일 제공과 이용허락 제한 없음은 확인했지만, 현재 실행 환경에서 원본 파일을 내려받지 못해 아직 데이터로 포함하지 않았습니다.
- 한식진흥원 [아카이브 레시피](https://www.data.go.kr/data/15136607/fileData.do): 제4유형(상업적 이용금지·변경금지) 조건으로, 기획의 상업적 활용·가공에 바로 채택하지 않았습니다. 재료 파일과 부모 레시피 파일의 이용 조건을 혼동하지 않습니다.
